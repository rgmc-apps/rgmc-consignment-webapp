### Item price bug (P0344528P0104 / RGMC / S00001) — ROOT CAUSE FOUND, BC-SIDE FIX APPLIED BY USER, VERIFIED RESOLVED

- **Root cause**: the Price List *header* S00001 was `status: "Active"`, but the individual Price List *line* for this one item (lineNo 505072, last modified 2026-09-21) was stuck at `status: "Draft"`. In BC's Price Lists feature, line-level status gates price calculation independently of the header — a Draft line is excluded from BC's own live price lookup (the `itemPrices` custom page, Pag50318) even though the header is Active. This is what the webapp's `/sync` duplicate/price-check endpoint (and the add-to-order flow) surfaces as "no longer has an active price."
- **Confirmed isolated to this one item** — a sibling item from the same brand/timeframe (`P0130007S0002` under S00002) had its line properly `status: "Active"`, ruling out a systemic sync bug.
- **Secondary finding (now resolved as a side effect)**: Firestore/GCS had a stale cached override price of ₱2299 for this item (from before the BC line was edited down to ₱1999 on 2026-09-21), while the Draft line itself held ₱1999. User confirmed **₱1999 (the BC value) is correct**.
- **Attempted fix #1 — failed**: wrote a one-off PowerShell script (not committed to any repo — ad hoc, run from the terminal) that pulled BC OAuth credentials from `rgmc-bc-api-prod`'s Cloud Run env vars via `gcloud run services describe`, obtained a token via the client-credentials flow, and sent a direct `PATCH` to `companies(RGMC)/priceListHeaders(cf0f0948-fd75-f111-8070-002248583930)/priceListLines(09c68936-a477-f111-8070-70a8a571e15c)` with body `{"status":"Active"}`. **Returned HTTP 200, but a follow-up GET showed `status` was still `"Draft"`** — only `lastModifiedDateTime` had bumped. BC's own business logic silently reverted the field; activating a price list line is a proper workflow action in BC (not a bare field write), and this custom API page doesn't expose that action for direct API calls.
- **Fix #2 — user did it manually in the BC UI** (Price Lists page → S00001 → line for P0344528P0104 → Activate action) and reported it done.
- **Verified resolved**, in this order, all against `rgmc-bc-api-prod`:
  1. `POST /bc/custom/v3/item-prices/P0344528P0104/sync?company=RGMC&on_date=2026-10-16` → `{"bcPrice":1999,"bcPriceListCode":"S00001","updated":true,"removed":false,"message":"Price updated: None → 1999"}`.
  2. `POST /bc/custom/v3/item-prices/refresh?company=RGMC` → triggered worker-pool rebuild of GCS catalog blobs (evicted catalog/families/search_index/price_list_headers/price_overrides caches).

- **BC has two distinct, independently-cached pricing data paths that can disagree**, and this is the crux of the whole price-bug investigation:
  1. BC's own live `itemPrices` custom page (Pag50318) — the *authoritative* source, consulted by `/sync` and (indirectly) the catalog build. It respects Price List **line-level** status (Draft lines are invisible to it even under an Active header).
  2. The Firestore `price_list_items` collection + its GCS `price_overrides.json` compact index — populated by a **periodic** worker-pool sync (`POST /internal/firestore/sync-price-list-items`), used only to overlay date-specific prices onto the GCS catalog blobs for dates other than the blob's own sync date. This can go stale relative to path 1 if BC data changes between worker syncs — exactly what caused the "2299 vs 1999" discrepancy seen in this session (the Draft-status edit on 2026-09-21 hadn't been picked up by this slower path by the time of the bug report).
  - When diagnosing a pricing discrepancy, always check **both** paths — don't assume the one that looks "complete" (header Active, line exists with a valid date) is the one actually feeding the live price check.
- **BC's Price List Line `status` field cannot be set via a direct OData PATCH** — confirmed empirically this session (200 OK, silent no-op). Any future "activate this line" need must go through the BC UI's `Activate` action; there is no working API path found so far, and none should be assumed to exist without re-testing.
