# Handoff

## Goal

Build end-to-end tracking of whether consignment-app orders that the webapp *thinks* were submitted actually exist in Business Central, and give users a way to fix the ones that don't — across three repos: `C:\claude\rgmc-consignment-webapp` (Ionic/Vue frontend), `C:\claude\rgmc-bc-api` (FastAPI backend), `C:\claude\rgmc-worker-pool` (Pub/Sub background worker).

Concretely, in three stages (all user-approved as they came up):

1. **Add a server-validated `inBc`/`inBcStatus` flag to every `session_history_{env}` Firestore record**, checked against BC directly (not trusted from the client) — `confirmed`, `not_found`, `needs_review` (ambiguous — never auto-resolved, see Context & Gotchas), `not_applicable` (no-sales), `unknown_company` (legacy, no company code to route a BC query), `pending` (not yet checked).
2. **Add a "Needs Retry" path in the webapp**: a filter chip + gated "Retry Submission" button on `HistoryPage.vue` that only appears once `inBc === false` is confirmed (not just on local `failed` status), restoring the session to the Submit screen for manual review+resubmit — explicitly **not** auto-resubmission (user's call, to avoid creating duplicate BC orders).
3. **Add a login-time notice** on `LandingPage.vue` (no such banner framework existed before) telling a user how many of their own sessions need retrying, linking into History's new filter.
4. **Move the heavy bulk-validation job out of bc-api and into rgmc-worker-pool** as a Pub/Sub-triggered background job, because running it synchronously inside an HTTP request proved infeasible at the collection's real size (~20k docs).
5. **Get the admin trigger endpoint properly represented in Swagger** (`/swagger` on bc-api) — it was accomplishing its task but invisible/undocumented as a distinct, discoverable group.

All five are implemented. Stages 1–3 and the Swagger polish for stage 5 are also validated by an actual production run; stage 4 (the worker-pool migration itself) is implemented and code-verified but **has not yet been exercised end-to-end in production** — see Current State.

## Failed Attempts

- **What was tried**: First `POST /session-history/verify-all` call (before any of the worker-pool migration work), synchronous in bc-api, 4 `ThreadPoolExecutor` workers, no skip-logic, client `--max-time 580`. **Why it failed**: curl exit 28 (client timeout) at exactly 580.003s, HTTP_STATUS:000 — no response ever received. **Root cause found later** (via the worker-pool research agent): bc-api's own BC semaphore (`bc_functions.py`, `threading.Semaphore(3)`) is shared with all live user traffic on that Cloud Run service — 24 (later) or 4 (original) worker threads were mostly just queuing on a 3-slot semaphore, not actually running concurrently. **Resolution**: this is exactly why the job was later moved to worker-pool, which has its own independent `_bc_semaphore(4)` in `bc_client.py`, decoupled from bc-api's live-request budget.
- **What was tried**: After the above timeout, assumed the request had simply failed and nothing happened server-side. **Why it was wrong**: a follow-up `GET /session-history` sample showed 11,540 records already had a definitive `inBcStatus` before any *successful* backfill call had been made — meaning the original (pre-fix) synchronous handler almost certainly kept running server-side well past the client's timeout (Cloud Run's configured request timeout for `rgmc-bc-api-prod` is 3600s, confirmed via `gcloud run services describe ... --format="value(spec.template.spec.timeoutSeconds)"`; FastAPI/Starlette doesn't necessarily cancel an in-flight sync-route thread just because the client disconnected). **Resolution**: none needed — this just meant the real remaining backlog for the two post-fix chunked calls was smaller than expected; not a bug, just a timing surprise worth knowing about if a similar "client timed out but check anyway" situation comes up again.
- **What was tried**: Assuming the collection was small enough for one request based only on `GET /session-history?company_code=RGMC&limit=500`'s `total` field. **Why it was misleading**: that endpoint's `total` is scoped to one company only (RGMC alone was 5,577); the real cross-company total (queried later by iterating all `/bc/companies` and deduping by `id` across paginated `GET /session-history` calls) was 19,744–19,745. **Resolution**: always get the true total via the full-collection stream (what `backfill_validate` itself does), not a single company's paginated list `total`.
- **What was tried**: Re-cancelling the original stuck background curl task via `ScheduleWakeup({stop: true})`. **Why it failed**: "Permission for this action was denied by the Claude Code auto mode classifier" (reason unexplained). **Resolution**: left the wakeup pending; it fired later as a stale, superseded instruction twice (harmless — the work it was checking on had long since been completed through other means by the time it fired). If this happens again, don't fight the denial — just let the stale wakeup fire and respond that it's superseded.
- **What was tried (not a real failure, a near-miss worth flagging)**: Initially wrote `tags=["Session History", "Internal"]` directly on the `verify_all_sessions` route decorator. **Why it would have been wrong**: `session_history_router` already has router-level `tags=["Session History"]`; FastAPI concatenates router tags + route tags (`fastapi/routing.py:990-992`), so this would have produced a duplicate `["Session History", "Session History", "Internal"]`. **Resolution**: changed to just `tags=["Internal"]` on the route; verified the final merged tag list via an actual `app.openapi()` call locally (`from src.main import api; api.openapi()` — note the FastAPI instance is named `api`, not `app`, in this codebase's `main.py`).

- **The `inBc`/`inBcStatus` design, in full** (needed to understand any of the code above):
  - Fields: `inBc: bool | None` (true=confirmed in BC, false=confirmed NOT in BC → retryable, null=not yet known or ambiguous), `inBcStatus: 'confirmed'|'not_found'|'needs_review'|'not_applicable'|'unknown_company'|'pending'`, `inBcCheckedAt: float | None` (epoch seconds).
  - History records don't store BC's `externalDocumentNo` — only `salesOrderSeries`/`returnOrderSeries` (BC's own document `number`). So verification matches on `number`, with a customer+postingDate fallback (same fields the webapp's pre-existing manual "Fetch BC Order Number" button in `HistoryPage.vue` already used) when no series is stored or the stored one doesn't resolve.
  - **Ambiguous matches (>1 candidate) are never auto-picked — flagged `needs_review` instead.** This is a direct, explicit lesson from an earlier-session bug (the "Thread C" history-mismatch incident — substring/loose customer matching once silently attributed the wrong BC order number to a session; fixed in that earlier session by making matching exact-only). Don't regress this if touching `_verify_side`/`verify_record` in either repo.
  - Retry is **restore-to-draft-and-navigate-to-Submit-for-manual-resubmission**, not automatic — explicit user decision, to keep a human in the loop before anything hits BC again (duplicate-order risk).
- **BC company short codes** (confirmed live via `GET /bc/companies`): `RGMC`, `CGI`, `KW1`, `LGAP`, `ANC`, `SBIC`, `USGI`, `BSG`, plus non-consignment-app companies (`RGMC - Core Build`, `SBICBackup`, `SBIC-CLEAN`, `TADC`, `TNRC`, `VDI`) that never appear in `session_history_{env}`.

  - `rgmc-worker-pool`'s `sync_worker.py` subscribes with `FlowControl(max_messages=1)` — a `verify-session-history` message shares this subscription/concurrency-slot with `routine-sync` and every other sync-worker job type, so triggering it while a nightly `routine-sync` is mid-run will queue behind it.
