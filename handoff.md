## Context & Gotchas

- **The user commits and pushes independently, mid-session, across all four repos, without saying so in chat.** Reconfirmed again this session — the item-price fix was committed, merged via PR, and auto-deployed to prod within the same session, all without an explicit heads-up in chat. Always run `git status --short` / `git log` / `git fetch && git log origin/master` before assuming your edits are still sitting uncommitted, and before assuming a repo's HEAD reflects the true latest state (local branches can trail `origin/master` by a merge commit even right after you made the edit).
- **BC environment-specific OData quirks, now confirmed in two independent code paths** (`sbic-manual-trigger-page/app.py`'s `_multi_field_contains_search`, and now `rgmc-bc-api`'s v3 item-price live search):
  - `tolower()` is non-functional on RGMC's custom BC API pages — wrapping a field in it makes `contains()` always return zero rows, regardless of input. Case-insensitivity must come from uppercasing the search term client-side instead, which works reliably because RGMC/SBIC's own data-entry convention stores `productNo`/`description`/`name`-type fields in ALL CAPS in BC.
  - A single `$filter` combining `contains(fieldA,...) or contains(fieldB,...)` across two **different** fields is rejected outright (HTTP 501 Not Implemented on Pag50318 v3.0; `sbic-manual-trigger-page`'s note describes a 400 `BadRequest_MethodNotImplemented` on a different custom page — same underlying limitation, different page/error code). The working pattern everywhere in this codebase is: one request per field, merge and dedupe the results in Python.
  - **Takeaway for any future BC custom-API search feature in this codebase**: always query one field at a time with the search term pre-uppercased; never rely on `tolower()` or a cross-field `or` inside a single BC `$filter`.
- **BC productNo vs. description formatting differs**: real BC productNo values have dashes/separators stripped (e.g. `D024S04700101`), while the human-readable description preserves them (e.g. `"D024-S0470 | S | BLUE I"`). A user typing a dash-formatted "stock number" they read off a description label will only ever match via the description field, never productNo — this is inherent to how the data is entered, not a bug, but explains why description-field search matters just as much as productNo search for real-world usability.
- **Investigation technique reconfirmed/reused this session** for ad-hoc live BC/Firestore checks without writing a committed script: PowerShell + the deployed `rgmc-bc-api-prod` service's own `/bc/token` endpoint for an access token (kept in-memory only, never written to disk — see Failed Attempts), then direct OData calls against `https://api.businesscentral.dynamics.com/v2.0/<tenant>/<environment>/<api-path>/companies(<id>)/<entity>`. Known constants: tenant `ca3ca144-09d9-42dd-920a-c72aedd54dd6`, environment `Production`, v3 item-price API path `api/rgmc/rgmccustom/v3.0`, company IDs for RGMC/CGI/KW1/USGI/LGAP all resolvable via `GET /bc/companies` on the prod service.
- **Claude-in-Chrome browser automation works well for direct BC web-client verification** when no API exposes the data needed (e.g. the No. Series master table isn't exposed via any standard or custom API in this environment) — ask the user for a bookmark/URL into their own logged-in session rather than guessing a tenant-specific URL, then use BC's in-app "Tell me what you want to do" search box to navigate from wherever the bookmark lands to the actual page needed.
